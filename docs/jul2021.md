This document records the July 2021 osu!standard performance-points
investigation. The target values come from the Wayback-based comparison table
in [CONTRIBUTING.md](../CONTRIBUTING.md). The goal is general historical
parity, not score-specific offsets or cached PP values.

## Current implementation

The implementation is in [`src/jul2021/`](../src/jul2021/), with
the public export and factory registration in [`src/index.ts`](../src/index.ts)
and regression coverage in [`src/index.test.ts`](../src/index.test.ts).

The implementation is a TypeScript port of the July-era osu!standard
difficulty and performance formulas. It reuses the existing February 2019
hit-object preparation and geometry helpers, while applying the July
difficulty and performance constants. The public rework name is `jul2021`.

The TypeScript implementation matches all 24 closer-oracle July fixtures
within the repository's strict 3-decimal test tolerance. No score-specific
correction has been added.

## Fixture policy

The checked-in `fixtures/*_jul2021.json` files use outputs generated by the
actual historical C# oracle through `OsuPpApi`. The generator is
[`scripts/generate-jul2021-fixtures.ts`](../scripts/generate-jul2021-fixtures.ts)
and builds the pinned oracle once before calculating every fixture from its raw
`.osu` map.

The score inputs, raw maps, live API PP values, and score metadata are
preserved from the `_oct2025.json` source fixtures. The fixture `rework_data`
records the pinned historical source so these generated expectations are
distinguished from the Wayback display values documented above.

The TypeScript `jul2021` calculator matches this closer oracle for the wider
fixture set. The oracle outputs remain checked in as the acceptance reference
rather than being regenerated from the TypeScript implementation.

## Map provenance

The three raw maps used for the July comparisons are beatmap IDs `164020`,
`129891`, and `550235`. The archived `164020` artifact was compared with the
checked-in map and parsed identically. The available evidence does not show a
map revision capable of explaining the remaining `0.0059165pp` residual.

All oracle runs used fresh `.osu` map parsing. Cached PP or cached difficulty
attributes were not used as the implementation.

## Formula and preprocessing checks

The following source boundaries were checked against the July implementation:

- The aim angle coefficient is `1.4` in the July snapshot. Replacing it with
  the older `1.5` value changes the result materially and fails the target
  cases, so the `1.4` value is retained.
- The July snapshot uses the logistic approach-rate bonus. Substituting the
  older bounded approach-rate bonus moves the DT case by about `0.107pp`, so
  that is not the residual.
- The difficulty section starts from the second difficulty object because the
  first map object is not yet a difficulty object in the historical source.
  Changing the section anchor did not move the failing value and regressed
  another case, so the original anchor was restored.
- Stacking with base AR instead of mod-adjusted AR changes the DT stack count,
  but does not move the failing PP value and regresses the HR case.
- The July source's speed and aim constants, strain reduction, star-rating
  combination, and PP component formulas agree with the current port.
- July uses the historical `1.00041f` circle-size fudge and does not apply the
  synthetic 36ms legacy tail shift used by the February 2019 compatibility
  path. The TypeScript port now scopes both behaviors by rework.

These checks rule out the obvious shared formula and preprocessing changes as
general explanations for the single small residual.

## Score-input checks

Several score interpretation hypotheses were tested across the target set:

- Recomputed accuracy and published/API-rounded accuracy do not produce all
  three Wayback values under one rule. The accuracy change needed for the
  first score is not the change needed by the other scores.
- Combo changes have a much larger effect than the residual and do not form a
  shared explanation for all three scores.
- The `CL` modifier is inert in the current July formula path. Removing it or
  changing Classic handling does not explain the isolated residual.
- `legacy_total_score` is a score-conversion field and is not consumed by the
  July performance formula in the tested path. Changing it cannot explain the
  result.
- The historical Classic/legacy slider-tail estimator is only relevant to a
  CSR path that is disabled for this July rework. It therefore cannot explain
  this case.

The score-input probes leave no valid general rule that changes only the
`244720292` result by the required amount.
