# November 2021 PP investigation

This document records the investigation into the historical osu!standard PP
values collected in [CONTRIBUTING.md](../CONTRIBUTING.md) for the November
2021 rework. It is intended to be the source of truth for generating
best-effort fixtures while preserving the distinction between a reproducible
calculation and a historical value that may have come from server-side state.

## Target values

The three historical values we are trying to explain are:

|  Score ID | Beatmap ID | Historical value | Mods  | Great |  Ok | Meh | Miss | Combo | Published accuracy |
| --------: | ---------: | ---------------: | ----- | ----: | --: | --: | ---: | ----: | -----------------: |
| 244720292 |     164020 |        564.057pp | DT HD |   467 |  12 |   0 |    0 |   651 | 98.32985386221294% |
| 176782980 |     129891 |        547.810pp | None  |  1941 |  40 |   0 |    2 |  2383 | 98.55437888720793% |
| 110536233 |     144029 |        507.523pp | HR HD |   674 |   7 |   0 |    0 |   988 | 99.31473323543808% |

The values above are the `nov2021` entries collected from the Wayback-based
comparison table in [CONTRIBUTING.md](../CONTRIBUTING.md#L54). They are not
the current live PP values. The current score pages show approximately 578,
472, and 521 PP respectively, while retaining the same stable hit counts and
combos. This is direct evidence that the displayed PP for these scores has
changed over time.

## Best reproducible approximation

The closest general calculation currently available is the raw-map
calculation from the late-November osu! source snapshot
`5a3be778a172405402bdcaadfdfdb7bb04ce190d` (12 November 2021), using the
checked-in `.osu` maps and the six stable hit counts above.

|  Score ID | C# snapshot | Independent C++ probe | Historical value | C# residual |
| --------: | ----------: | --------------------: | ---------------: | ----------: |
| 244720292 |  564.065073 |            564.064819 |          564.057 |   -0.008073 |
| 176782980 |  547.810026 |            547.809998 |          547.810 |   -0.000026 |
| 110536233 |  507.523862 |            507.523773 |          507.523 |   -0.000862 |

The C# and C++ implementations are independent enough that their agreement
shows the residual is not a local TypeScript or wrapper error. The C++ probe
uses single-precision operations and the C# implementation uses double
precision operations; both land at the same practical result.

## Map provenance

The raw maps are not stale local copies. Each checked-in map was downloaded
again from `https://osu.ppy.sh/osu/{beatmap_id}` and compared byte-for-byte:

| Beatmap ID | Bytes | SHA-256                                                            |
| ---------: | ----: | ------------------------------------------------------------------ |
|     164020 | 19119 | `2869C686C2AC6A8FF87A36B6C289C7D7DF247EA3084CF5350537AFEE6FAD1B9C` |
|     129891 | 50880 | `D82101C8C51A8B95EEEFB7535E18C76F05D1651040232811BAA0084EA1F89C12` |

This rules out a changed `.osu` file as the explanation. It does not rule out
historical server-side difficulty attributes or a stale difficulty cache,
because those attributes may have been calculated by a different binary or
preprocessing state than the current raw-map calculation.

## Historical score and statistics path

The November 2021 osu! client source has two relevant boundaries:

1. `APIScoreInfo.CreateScoreInfo()` appends `ModClassic` to API scores and
   copies the API's legacy `count_*` fields into `ScoreInfo.Statistics`.
   It does not synthesize slider ticks, alter the main hit counts, or derive a
   different accuracy value during this conversion. See `osu/osu.Game/Online/API/Requests/Responses/APIScoreInfo.cs`.
2. `OsuPerformanceCalculator` reads `Score.Accuracy` directly for aim and
   speed scaling. Its accuracy component separately uses the integer great,
   ok, meh, and miss counts, with hit-circle count from the difficulty
   attributes. Its `totalHits` is the sum of those four main counts. See `osu/osu_nov2021_5a3be77/osu.Game.Rulesets.Osu/Difficulty/OsuPerformanceCalculator.cs`.

The local wrapper mirrors that handoff in
[PpCalculator.cs](../OsuPpApi/PpCalculator.cs#L25). For the November path it
creates a `ScoreInfo` with the supplied accuracy, combo, main hit counts, and
mods, then calls `calculateLegacy()`. `legacy_total_score` is only assigned
on the newer calculator path and is not consumed by the November calculation.

The API score format used for these stable plays exposes only the classic
main hit counts. Nested slider statistics are not present in the historical
score payloads used here. The wrapper has generic support for
`SliderTailHit` and `LargeTickMiss`, but the November source does not make
those generic additions part of the effective `totalHits` path for these
inputs. Preserved probes with and without reconstructed nested slider data
did not move the three relevant results to the historical values.

## Hypotheses tested

### Map revision

Rejected. Current API map downloads are byte-identical to the local fixtures.

### Cached PP

The live score pages demonstrate that PP is mutable historical state: the
same stable scores now display approximately 578, 472, and 521 PP. Cached PP
cannot be used as the implementation because the goal is a general
calculation, but this strongly suggests that the Wayback values were produced
by a historical server binary.

### Cached difficulty attributes

Still plausible. A stale or submission-time difficulty cache can differ from
the result of recalculating the current map with a later source snapshot even
when the `.osu` bytes are unchanged. This is the strongest remaining
non-score-specific explanation, but the original cached attributes have not
been recovered.

### Accuracy precision

Rejected as a general rule. The exact accuracy values recomputed from the
integer hit counts are:

```text
244720292: 0.9832985386221294
176782980: 0.985543788872079
110536233: 0.993147332354381
```

Matching the historical PP values by changing only the supplied accuracy
requires approximately:

```text
244720292: 0.9832863315908791
176782980: 0.9855433005908291
110536233: 0.9931458675106309
```

Those values are not produced by the published hit counts, percentage
rounding, or one shared precision rule. They are useful diagnostics, not valid
fixture inputs.

### Combo or effective-miss inference

Rejected. The score combos are 651, 2383, and 988, and the map max combos are
652, 2385, and 990. The November calculator uses combo scaling and estimates
slider breaks from combo, but changing combo by one produces a much larger
effect than the residual for the first score and does not explain all three
scores through one rule.

### Slider tails, large ticks, and slider-head accuracy

Rejected for this score set. The historical API payloads do not contain the
extra nested statistics, and adding or removing reconstructed slider-tail
statistics does not produce the requested values in the November path. The
`NoSliderHeadAccuracy` setting on `OsuModClassic` affects gameplay judgement,
not a hidden transformation of the six API hit counts in the performance
calculator.

### `legacy_total_score`

Rejected. The legacy score totals are useful for ScoreV1 score conversion, but
the November PP formula does not read them. Changing them cannot explain the
residual.

### Score V2 and arithmetic mode

Rejected. Score V2 changes the results by many PP on these cases, rather than
by the observed residual. C# double arithmetic, C++ float arithmetic, and
compiler optimization variants all agree closely with the late-November
result but do not produce the first target exactly.

### Alternate November source snapshots

Rejected as a shared explanation. Several nearby osu! snapshots and
third-party ports were tested. They produced materially different values on
at least one of the three scores, while the late-November snapshot is the only
family that consistently lands near all three targets.
